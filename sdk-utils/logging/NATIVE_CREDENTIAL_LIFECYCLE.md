# Native logging lifecycle reset

The native adapter compares `paymentSessionConfig.sdkAuthorization` before adopting new props. A nonempty changed SDK authorization starts a fresh logging lifecycle: existing counters/once keys, SDK-init timing, attempt and context identity are reset, then the incoming native props configure the logger and initialize timing. When SDK authorization is absent, a nonempty changed `clientSecret` is the legacy fallback. SDK authorization takes precedence if both are present. With neither credential present no new lifecycle is inferred. Ordinary rerenders, payment-ID-only changes, native root changes and sheet reopen with unchanged authorization do not reset the state.

No session ID is generated. The comparison retains only the current credential kind and string reference in memory, replaces it on change, and never emits/persists credentials or a derived key. It is retained across sheet close so reopening with the same authorization is not mistaken for a new lifecycle. The comparison is shared by native roots on the existing module instance; this is a sequential lifecycle fix, not arbitrary concurrent-root isolation. Existing captured async contexts are not mutated by reset; the existing global runtime/unknown-ID backfill limitations remain.

Android's demo reload reads an `sdkAuthorization` response field despite the button's client-secret wording; it closes the previous native PaymentSession and initializes a new one. A new authorization therefore rearms mounted/rendered/first-interaction milestones even while session_id stays empty. Web controllers do not call this native preparation hook. Existing handling of supplied nonempty session IDs remains unchanged.
